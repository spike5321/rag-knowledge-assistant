# 文档 → 向量库：知识库构建工具

把一堆 `.md` / `.txt` / `.pdf` 变成一个**可检索的向量库**。

它是给 Agent 系统准备检索层用的，不是又一个"上传文档然后聊天"的问答机器人 ——
主体是两条命令行，界面只是可选的人工核对工具。

## 它解决什么

任何"基于资料回答"的 Agent，第一步都是把资料切成能检索的片段。这一步看着简单，
但**切分质量直接决定检索效果的上限**：片段切坏了，后面换多好的向量模型都救不回来。

这个工具做三件事：

| 命令 | 作用 |
|---|---|
| `python -m rag.ingest` | 解析 → 切分 → 向量化 → 写入 Chroma。幂等：内容没变就跳过，变了就覆盖 |
| `python -m rag.query` | **只检索、不生成回答** —— 用来判断"库建得对不对" |
| `streamlit run app.py` | 可选的可视化界面，人工核对命中的片段对不对 |

`rag.query` 是刻意不加生成环节的：检索质量是入库质量的直接体现，一旦掺进大模型的
生成能力，就分不清"答得不好"是切分的问题还是模型的问题。

## 与 MockMate 的关系

同一套算法，两个形态：

| | 独立形态（本仓库） | 内嵌形态（MockMate） |
|---|---|---|
| 位置 | `rag/ingest.py` | `mockmate/kb/store.py` |
| 向量由谁算 | `rag/core.py`：智谱 embedding-3 或本地 bge | 由 Agent 的 LLM 客户端传入（Agent 换模型不必动存储层） |
| 由谁调用 | 命令行 | Agent 的工具（`search_jd_kb`） |

[MockMate](https://github.com/spike5321/mockmate) 是一个自己实现调度循环的面试 Agent 系统。
它需要"按 JD 检索面试考点"的能力，那份检索层就是从这个仓库长出来的。

所以本仓库的定位是**给 Agent 系统准备检索层的工具**，而不是一个平行的问答应用。
切分算法在这里可以独立跑、独立测、独立做 A/B 对照，不用把整个 Agent 跑起来 ——
这是把它单独留一个仓库的理由。

> 两边是直接 vendoring，没有抽成 pip 包：为一个个人项目维护发版流程和版本漂移
> 不划算。一致性靠单测 + 下面的对照脚本保证。
>
> 仓库名保留了历史（早期版本是个 Streamlit 问答应用 MVP），功能与定位以本文档为准。

## 快速开始

```bash
conda create -n rag-agent python=3.13 -y
conda activate rag-agent
pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
```

建库（默认读 `data/docs/`）：

```bash
python -m rag.ingest                # 增量入库
python -m rag.ingest --rebuild      # 清空后重建
python -m rag.ingest 我的资料/       # 也可以指定目录或文件（目录会递归展开）
```

验证检索（不会生成回答，也就不消耗对话额度）：

```bash
python -m rag.query "试用期是多久，考核怎么算"
python -m rag.query "报销标准" -k 3 --full
```

**不配 API Key 也能跑。** 向量化有两个 provider：配了 `ZHIPU_API_KEY` 走智谱
`embedding-3`；**没配就自动用本地 `bge-small-zh-v1.5`**（fastembed，首次运行下载约 100MB，
之后完全离线）。想固定用某一个就设 `EMBEDDING_PROVIDER=zhipu|local`。

> ⚠️ 两个 provider 的向量维度不同（2048 vs 512），**切换后必须重建向量库**：
> `python -m rag.ingest --rebuild`。

可选界面：

```bash
streamlit run app.py
```

## 切分质量：实测

下面每个数字都能用仓库里的脚本复现，命令在每节末尾。

### ① 按标题切 vs 按字数切

语料是三篇结构完整的 markdown（同一套参数 `CHUNK_SIZE=500`）：

| 语料 | 旧：按字数累加 | 新：按标题切 |
|---|---|---|
| `redis_points.md`（1643 字） | 4 个片段 | **9 个片段** |
| `http_network_points.md`（1568 字） | 4 个片段 | **8 个片段** |
| `system_design_points.md`（1652 字） | 4 个片段 | **9 个片段** |

片段数变多不是目的，**边界落在哪里**才是。旧版最长的那一片开头长这样：

> **三者的区别一句话说清**：穿透是"查不存在的"，击穿是"一个热点过期"，
> 雪崩是"一大批同时过期或整体挂掉"。
> \#\# 二、缓存与数据库的一致性
> 主流策略是 **Cache Aside**：先更新数……

一个片段里挤了「穿透 / 击穿 / 雪崩」三个知识点，还顺带跨进了下一节。新版同一个位置：

> 【1. 缓存穿透】
> **现象**：查询一个数据库里也不存在的 key。缓存永远不命中，请求全部穿到数据库。

把"串味"量化一下：

| 两个知识点出现在同一片段 | 旧 | 新 |
|---|---|---|
| 缓存穿透 + 缓存击穿 | 1 个片段 | **0** |
| 缓存穿透 + 缓存雪崩 | 1 个片段 | **0** |
| 缓存击穿 + 缓存雪崩 | 1 个片段 | **0** |

复现（脚本内置修正前的算法，是从 git 历史里原样抄下来的，不是凭印象重写的近似版）：

```bash
python scripts/compare_chunking.py                  # 跑 data/docs/
python scripts/compare_chunking.py 你的文档.md        # 跑指定文件
```

### ② 无空行的 PDF 文本

pypdf 抽出来的文本通常一行一段、几乎没有空行。949 字的构造用例（60 行）：

| | 片段数 | 各片段长度 |
|---|---|---|
| 旧 | 3 | 500 / 500 / 109 |
| 新 | 2 | 485 / 463 |

旧版的边界落在**字符位置**上，和文本自身的行结构无关；新版落在行首。

这一条属于"边界质量"的小修正，**不是数量级差异** —— 别把它讲成解决了什么大问题。
真正的收益在第一张表。

### ③ 检索链路

```
$ python -m rag.query "社保基数什么时候调整" -k 2
问题: 社保基数什么时候调整
命中 1 个片段

[1] 相似度 0.415   来源 新员工入职指南.pdf
    新员工入职指南 试用期说明 新员工试用期为三个月，自入职之日起计算……
```

注意「**命中 1 个片段**」：`data/docs/` 里那份示例 PDF 只有 340 字，整篇就是 1 个片段。
这恰好演示了问题本身 —— 文档不分节，检索就只能把整篇丢给你，相似度也因此被稀释。
要看出切分的价值，得给它一份真文档。

### ④ 入库状态（真实运行）

```
$ python -m rag.ingest --rebuild
扫描到 1 个文件，重建模式将清空现有向量库
  [新增] 新员工入职指南.pdf 1 个片段

新增 1 个片段，更新 0 个片段。向量库现有 1 个片段。
下一步可以先验证检索效果: python -m rag.query "你的问题"
```

四种状态：`新增` / `更新`（同名文件内容变了）/ `跳过（内容未变）` / `失败`（单个文件出错
不影响整批）。后两种由离线单测覆盖，见 `tests/test_ingest.py`。

## 三条设计决策

**1. 先按 markdown 标题切小节，小节内再按段落聚合。**
片段前面会带上所属小节标题（`【2. 缓存击穿】`），这样下游拿到片段就知道
"这段话在讲哪个知识点"，而不是一段没头没尾的正文。切不出段落时（PDF 常见）退回按行切。

**2. 靠内容指纹决定"跳过"还是"覆盖"，不是靠文件名。**
原实现是「这个文件名已存在 → 整篇跳过」，而且不报错。所以文档改了内容重新入库
**永远不生效，还完全静默** —— 向量库里一直是旧内容，日志上却显示"已跳过"。
现在片段 id 是 `文件名::序号::内容hash`：指纹完全一致才跳过，变了就替换。

**3. provider 由"有没有 Key / 服务端是否报错"决定，且默认偏向"能跑起来"。**
`auto` 模式下没配 Key 就直接走本地，而不是先发一个注定失败的请求再降级 ——
少一次无效调用，也少一段"必须联网才能触发"的分支。但显式设了 `EMBEDDING_PROVIDER=zhipu`
时绝不偷偷降级：两个 provider 的维度不同，静默切换会让检索结果错得看不出来。

另外两处细节：**先向量化再删旧数据**（网络挂了旧索引还在，不至于查不到东西）；
片段 id 从 `文件名::序号` 改成带内容指纹，内容变了 id 就变。

## 目录结构

```
rag/core.py                   模型调用的唯一入口（智谱 / 本地 fastembed 双 provider）
rag/ingest.py                 文档解析、切分、入库 + 命令行
rag/query.py                  只检索不生成的命令行
rag/pipeline.py               检索 + 生成（界面用）
rag/mock.py                   模拟数据层（Demo / 测试用）
app.py                        可选的可视化验证界面
scripts/compare_chunking.py   切分新旧对照脚本
scripts/make_sample_pdf.py    示例 PDF 生成（验收用一次性脚本）
tests/                        单测（离线，不联网）
data/docs/                    默认语料目录
db/                           Chroma 持久化（gitignore，可用 --rebuild 重建）
```

## 测试

```bash
python -m pytest tests -q      # 35 项，离线、不联网、约 7 秒
```

原来 25 项，这次补的里面有两组是**回归测试**，钉住上面第 1、2 条设计决策：

- `test_sections_are_not_mixed` —— 同一片段里不允许出现两个知识点
- `test_changed_file_is_really_updated` —— 文件改了内容，向量库里的旧片段必须被真正替换
- `test_no_blank_lines_falls_back_to_line_split` —— 无空行文本不许退化成整篇一片
- `test_explicit_zhipu_does_not_fall_back_without_key` —— 显式指定 provider 时不许静默降级

## 已知限制

- **只有纯向量检索，没有混合检索 / rerank。** 专有名词（"LRU"、"三次握手"、"RRF"）
  在向量空间里语义是虚的，召回偏弱 —— 缺一路关键词召回（BM25）是当前最大的短板。
- **切分只认 markdown 标题**（`#`~`####`）。PDF / DOCX 没有标题结构，只能退回按行、
  按段落切，拿不到"一节一片段"的效果。
- **本地向量模型本机没有下载过**：降级分支只有单测覆盖（用桩替换），
  **没有端到端实测过**本地模型的检索效果。
- **provider 切换没有前置检查**：切错了要到检索时才报维度不匹配。应该把 provider
  和维度写进 collection metadata，检索时对不上就直接报错。
- **没有评测集。** 上面那张"串味"表是**结构性指标**，不等于检索准确率提升 ——
  后者要用带标注的问题集来量。
